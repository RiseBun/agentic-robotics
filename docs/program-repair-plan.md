## 问题本质

stack/restack 需要多个阶段；正常抓取阶段在尚未抬升时不能验证持有，因此按现有协议不声明持有后置条件。这种“未声明验收”不是失败。

真实模型 restack/83 中，正常抓取完成后出现一次状态字段读取错误。恢复上下文将这两段计为两次无进展，优先推荐人工帮助，覆盖了程序修正建议；模型因此提前退出。Runtime 只报告 KeyError 的 `0`，API 文档也未明确写出 get_execution_state 的字典结构。

## 实施顺序

1. 明确 API 返回结构：状态是字典，位姿字段为 tcp_xyz/tcp_wxyz；视觉定位与抓取采样仍返回原序列。只澄清真实接口，不添加猜测兼容分支。
2. 给字段访问错误提供可修复诊断：访问的键／索引、容器类型、公开字段名和代码位置，不把它归因于机器人或传感器故障，不泄漏额外状态。
3. 修正恢复判断：正常完成且未声明后置条件的阶段不算失败；最新程序错误应优先提出修正路径，即使相关物理事实没有变化。已修正的旧语法错误不能持续压过后续真实物理故障；重复失败代码、未知支撑下放置及总预算限制继续有效。
4. 单元／集成回归覆盖“正常抓取→一次字段错误→改正并抬升”、两次实际无新证据失败、错误修复后转为物理失败、迟到模型回复和目标切换。先验证恢复上下文，再做固定公开准备的模型交接和自然任务回归，分开报告。

通过标准：能在同一场景和累计预算下修复一次字段访问错误并继续验证；不能把软件修复当成物理成功，不能为了强制继续而屏蔽用户协助，也不能重置环境掩盖失败。

## 当前实现边界

- 状态 API 文档明确字典字段；运行期下标错误保留键／索引、容器类型、行列和有限公开字段名，不附带容器值。API 内部自己的 KeyError 保持 api_exception，不误归因为模型代码。
- 恢复上下文 version 2 保留原始尝试，另统计连续被阻塞尝试。正常完成且未声明后置条件的阶段不增加失败次数，也不证明抓持成功。最新 invalid_program 优先建议修正；后续成功或真实物理错误清除该修正建议。相同失败代码、重复 observe/finish、Runtime 前置条件和累计预算继续有效。
- 协调器回归覆盖修正后继续、修正请求期间停止及换目标；同一 episode 和原决策账本保留，旧回复不派发。
- 当前真实诊断只证明代码修正后能继续到公开持有验证，不证明完整重堆叠、统计收益或避免所有过早求助。

用户已指定真机接口暂时留空；机械臂型号、控制器、SDK／ROS 和相机读取接口均待后续填写，不阻塞当前仿真验证。
