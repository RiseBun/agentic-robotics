# 真实模型恢复决策：两种受控协议场景

日期：2026-11-26。只修改 Thor；生产服务、主模型配置、任务预算及验证阈值未变。

## 目的和范围

上一轮证明 Runtime 能阻止同条件重复派发，本轮检验既有主模型是否会自行提出改变取证方式或请求帮助。新增离线实验 fixture 服务，产品接口和在线权限不变。该服务为 synthetic TabletopFixtureBackend，使用符号事实模拟支撑物证据缺失；没有 RGB-D 物理遮挡、真实机器人或独立物理评分，不能报告机器人恢复成功率。

同一主模型、提示词和预算，各运行一次可恢复/持续未知条件。用户指令只有“将蓝色方块放在灰色支撑物上，夹爪留空”，没有给恢复计划。所有决定由真实模型生成。初次到达放置阶段才触发支撑物证据缺失；撤回不修复故障。只有模型显式调用检查并执行受限视角后，可恢复条件才恢复证据。持续条件最多两次视角，仍返回 unknown。

## 结果

| 条件 | 模型选择的技能序列 | 决策 | 调用 | 结果 |
|---|---|---:|---:|---|
| 可恢复证据缺失 | 抓取→放置失败→撤回→检查可见性（实际视角）→检查支撑几何→重新放置 | 9 | 20 | fixture 公开完成 |
| 持续未知 | 抓取→放置失败→撤回→检查（两次视角仍未知）→模型请求帮助 | 8 | 13 | 确认保持，等待用户 |

两个任务均关闭后审计：目标未变化、同一环境创建、未超预算；故障持续期间无成功夹爪释放记录。持续条件在未知后没有重新执行放置，也没有错误完成声明。详细断言和事件 ID 见 audit.json。单条行为记录只证明该提示和人工故障下出现了适当选择，不证明广泛稳定性或因果性能优势。

## 实现与复现

- cap-runtime/experiments/model_recovery_fixture.py：隔离的故障服务，不进入生产 Runtime 默认后端。
- runtime/scripts/model-recovery-fixture-probe.mjs：只读取现有模型配置，按顺序执行两种场景，保存原始交互并关闭任务。
- cap-runtime/tests/test_model_recovery_fixture.py：验证故障只由有效取证解除、撤回不能解除、持续未知不能释放或增加视角预算。

在已配置模型的 Thor 项目根目录：

```bash
node runtime/scripts/model-recovery-fixture-probe.mjs research/new-model-recovery-probe
```

输出目录必须全新。模型密钥不写入报告，执行预算累计且保留原失败。

## 工程检查

Python 413 项、Node 132 项通过；包含两个新增故障 fixture 回归。测试结果仅作为工程验证，不计机器人成功率。

## 仍缺少什么

- 实际 MuJoCo RGB-D 遮挡下的真实模型恢复对照，以及独立物理验收。
- 更多对象/目标、重复运行和冻结测试，不能把两次 fixture 行为当成统计收益。
- 任务理解歧义、能力不足和目标组合的独立评测。

下一步应把这个失败机制改为实际观测层的受控遮挡，检查同样策略是否产生有效的新像素证据；不能仅靠放宽 verifier 或让模拟器直接宣布故障消失。
